01 · CONTEXT

这些不是四个独立大项目，而是一个企业产品里的连续设计切片。

Content Space 面向内容检索、管理、选图和模板操作。它的难点不在于增加更多组件， 而在于让用户在高信息密度下理解字段、快速完成批量任务，并在复杂状态中保持可追踪。 我参与多个 feature workstream，通过小需求持续建立对企业级系统的整体理解。

02 · WORKSTREAMS

四个切片，共同证明一套 B 端问题解决能力。

GALLERY FILTER

高频筛选外露

将 Source 与 Project Name 移出复杂筛选树，同时避免把名称相似但业务语义不同的 China / Global 与 Local / Global 错误合并。

能力：信息架构 · 父子三态 · 高密度布局
AI-ASSISTED SEARCH

从 AI Search 到 Intent-to-Filter

先验证现有搜索能力，再将自然语言拆成语义查询与结构化条件； AI 先给出可编辑建议，用户确认后才进入标准筛选系统。

能力：问题定义 · Human-in-the-loop · AI 退出机制
FUTURE PRICE

从价格下拉追到数据契约

拆分时间维度与价格类型，明确单行具体记录和批量默认规则不是同一语义， 并持续追问可空日期、无未来价与部分失败。

能力：字段语义 · 批量规则 · 可空与异常数据
OPERATION LOG

让 Restore 成为可追溯的闭环

将列表扫读与完整详情分层，并通过确认、完成反馈、新增恢复日志与旧动作禁用， 区分历史事件和对象当前状态。

能力：状态建模 · 审计追溯 · 防重复操作

03 · SHARED METHOD

在画界面之前，先建立可以被产品和开发共同理解的模型。

SEMANTICS

相似文案不等于相同字段。

先确认数据来源、层级和映射，再决定信息架构与组件关系。

LIFECYCLE

不在成功页面停止。

继续检查 Clear、失败、部分成功、重试、撤销和退出条件。

BULK ACTION

批量操作不是把单行控件放到表头。

每个对象如何决定最终值、缺少数据时怎么办，都必须被定义。

FEASIBILITY

先确认系统已有能力，再决定是否新增 AI。

把 Search API、facet、filter action 和状态传递作为设计输入。

04 · OUTCOME

价值不在页面数量，而在于减少错误假设和开发返工。

这些 workstream 已形成筛选信息架构、AI Search 主流程、价格选择与批量规则、 Operation Log 与 Restore 状态等设计产出。它们处于不同的评审和开发阶段， 因此本案例重点展示我如何澄清复杂问题，而不把所有方案统一描述为已上线。
